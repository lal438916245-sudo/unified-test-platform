闭环差距分析与达成路径统一游戏测试平台 · 2026-09-29

目标：三引擎（pytest / Locust / matcheval）集成于一个平台，覆盖 UI 测试 · 压力测试 · API 测试。 当前两个被测系统（PrivaHigh、ColyseusTechDemo-MMO）是"手头缺一个既有 UI 又能联机进房的游戏"的替代方案。

平台本体：已闭环 真实链路：2 / 3 引擎 单一 SUT 三引擎：0 / 1 关键结论：闭环只差 3 件事

一句话结论

平台的"机械部分"已经闭环（计划 → 执行 → 报告 → 配置，四件事全通，且 pytest / matcheval 都已在真实资产上跑通并留档）。 差的不是平台能力，而是"真实数据的第三类覆盖"与"资产归属同一个被测系统" —— 具体三件事： ① 压测从未真实执行过；② 三类资产分属两个 SUT；③ 真实数据上的报告对比 / 趋势还没验证过。

而下面的关键发现表明：你不一定需要那个"完整游戏"就已经能拿到单 SUT 三引擎闭环。

3. 关键发现：你不一定需要那个"完整游戏"

PrivaHigh 自带的后端就是一个完整的、有 12 个 REST 路由的 HTTP 服务，而这正好是 Locust 的天然靶子：

@app.get   /health                    @app.get   /v1/game/state
@app.get   /v1/saves                  @app.post  /v1/actions
@app.post  /v1/saves/{slot}/new       @app.post  /v1/events/{event_id}/resolve
@app.delete /v1/saves/{slot}          @app.post  /v1/semester/advance
@app.post  /v1/game/new               @app.post  /v1/game/add-funds
@app.get   /v1/game/cohorts           @app.get   /v1/game/report/{semester}
统一鉴权：Header X-Game-Token（main.py:29 require_token，缺失即 401）

也就是说：PrivaHigh 这一个被测系统就能同时承载三类能力 ——

  • API 测试：pytest（49 条，已有）
  • UI 测试：matcheval（23 模板 / 5 场景，已有）
  • 压力测试：Locust 打上述 12 个路由（缺，但只需新增一个受控场景 + 一个新 locustfile）

反观另一条线：MMO 的服务端是 Node / TypeScript（colyseus-demo-server/src，5 个 room 全是 .ts，零测试文件）， 而平台只有 pytest 引擎（Python）→ 用 MMO 凑齐"三引擎"这条路在现有引擎集下走不通，它天生只适合承担"联机 + 压测"这一环。

路线做法能否达成"单 SUT 三引擎"前置/代价
A · 双 SUT 分开闭环 PrivaHigh 跑 pytest + matcheval（已完成）；MMO 单独跑 Locust 不能（按 §0 口径永远是两套验收） 需授权改 locustfile.py 的 WS 地址为受控配置 + 拉起 :2567 + 起 MMO 客户端
B · PrivaHigh 单 SUT 三引擎
（推荐）		 pytest + matcheval（已有）+ 新增 Locust 打 PrivaHigh 后端 12 个 REST 路由 能 —— 三引擎全部指向同一个被测系统 需授权：① 新增 1 个受控 locustfile 场景 key（平台白名单）② 新增 1 个 locustfile 脚本 ③ 新增 1 个 Environment（127.0.0.1:8765）④ 以固定端口 + 令牌启动后端

两条路线不冲突：B 先把"单产品三引擎"闭环做出来（这是平台能力的证明），A 作为"联机线"的独立验收另建计划。 未来一旦有"既含 UI 又能联机进房"的游戏，只需换资产与场景登记（matcheval 换素材、locust 换场景），平台架构不用动。

6. 到闭环的最短路径（推荐顺序）

#动作产出需要的授权
1平台重跑 PrivaHigh pytest 步骤把「49 passed」留档为新业务基线（不覆盖历史）执行授权
2新增受控 Locust 场景 privahigh-api + locustfile可压测 PrivaHigh 后端的受控场景白名单 + 新脚本授权
3以固定端口 + 令牌启动 PrivaHigh 后端压测目标可达（127.0.0.1:8765）+ 受控 Environment启动授权 / 你手动启动
4建一份三引擎计划：pytest → matcheval → Locust单 SUT 三引擎首次闭环，含配置快照与三份报告执行授权
5同一计划再跑一次（或改一个参数）做 A/B 对比真实数据上的对比 / 趋势能力验证执行授权
6复跑平台 verify 基线改动后的回归证据执行授权

7. 需要你定的三件事

  1. 走路线 B 吗？（用 PrivaHigh 的后端 API 承担压测，从而一个被测系统集齐三引擎）—— 还是先按 A 把 MMO 的联机压测单独跑通？
  2. 若走 B，是否授权新增 1 个受控 locustfile 场景 key（平台白名单登记）+ 1 个新 locustfile 脚本（打 12 个路由，带 X-Game-Token，令牌只存引用名不落明文）？
  3. 压测边界：目标即本机 127.0.0.1:8765（PrivaHigh 后端，非生产）；并发参数建议保守起步（users=3 / spawn_rate=1 / run_time=30s）由你确认。
