3. 关键发现：每连接约 7 秒被系统性中止

算术：653 次 entityUpdate ÷ 9 条连接 ≈ 72.6 次/连接；循环内是 send + time.sleep(0.1)（≈10 次/秒） → 每条连接实际只维持约 7.2 秒，而脚本设定单局 random.randint(10, 20) 秒。 每隔约 7 秒就抛一条 10053，9/9 无一例外。

3.1 一处必须更正的归因

上轮（10s）我的说法本轮（60s）的事实
「2 条 10053 是 run_time 到点关停导致连接被切断的副产物」 不完整：60s 窗口下每条连接仍在约 7 秒被中止，与关停无关。上轮因为窗口太短（每条连接最多只活 7~9 秒）恰好掩盖了这一点。

3.2 已排除的方向：不是载荷/契约问题

核查点源码证据结论
entityUpdate 里的属性名 RoomState.ts:10-12：xPos/yPos/zPos 都声明为 @type("number") 脚本发的 ["xPos", x, "yPos", 0, "zPos", z] 与声明一致 ✓
事件 id 的对齐 MMORoom.ts:119 用 client.id 作为 networkedUsers 的 key；:282 用 entityUpdateArray[0] 比对 脚本发的 seat sessionId 即 client.id ✓
服务端处理是否抛错 MMORoom.ts:170-194：找不到 id 只 logger.info 后 return，不抛异常 不会因载荷不符而崩溃 ✓

3.3 最可能的方向（待证实，不作为结论）

  • 脚本「只发不读」：对局循环里只有 ws.send，从不 recv。而 MMORoom 会持续向客户端广播状态补丁 → 接收缓冲区积压，达到临界后连接被中止（约 7 秒的稳定间隔符合"积压到阈值"的行为）；
  • 旁证：本仓库 Server/loadtest/ 用的是官方 colyseus-loadtest 客户端（会消费状态）， 与压测脚本的"裸 socket 只写"行为不同；
  • 决定性证据在服务端侧，而它只写 console、不落文件（helpers/logger.js 仅 winston.transports.Console）→ 需要看你启动服务端那个终端，重点找：Attempted to update client with id …（MMORoom.ts:174）、onLeave / 断连 / 站内异常。
