Part B · 八问作答

B.1 TestCase 到底代表什么？

TestCase = 「一个可复用的测试定义」（定义层）；Job = 「一次实际执行」（执行层）。 二者的分界线在当前代码里已经存在且清晰：plans.steps 是定义（可编辑、有 revision）， jobs 是执行（有 status/exit_code/log_path/started_at/attempt，状态机不可回退）。
应保存什么不应保存什么（依据）
TestCase engine + 受控 params（含 timeout_sec）+ requires_exclusive + name/description + revision + enabled 执行态一切字段（status/exit_code/时间/日志路径）—— 那些属 Job（domain.py:157-181）； Environment / Executor / AssetSource 的 ID —— 属 Plan（db.py:60-73）
Job 继续保存：plan_run_id / engine / name / 解析后的 params / timeout_sec / requires_exclusive / config_snapshot / status / exit_code / 产物路径 / retry 链 不需要改任何字段
Plan 继续保存：三个引用 ID + steps（顺序）+ fail_fast + owner + revision 不保存用例内容副本（否则两个事实源）

验证「TestCase 不应绑定 Environment / Executor / AssetSource」—— 与当前代码一致

候选绑定代码证据结论
EnvironmentPlan 已持有 plans.environment_id，Job 在执行时从 plan 复制（router.py:420）； build_config_snapshot 把它固化进 Job ❌ 不应绑定。会造成「计划环境 vs 用例环境」双源；且同一用例无法跨环境复用（比较/回归的前提就没了）
ExecutorPlan 已持有 plans.executor_id；「哪个引擎能在哪台跑」由 executors.allowed_runners（scheduler.py:271-274）+ _ENGINE_DEPS（config_center.py:157）表达 ❌ 不应绑定。解释器需求已由 engine 推导，再绑是冗余且会打架
AssetSourcePlan 已持有 plans.asset_source_id；实际数据集由 _asset_key_for(asset, engine) 注入（router.py:448-453） ❌ 不应绑定具体 ID；但应允许声明种类（见 asset_kind）

→ 审计报告的结论 经代码复核成立，并补一条更精确的表述： 「用例声明"我要跑什么"，计划声明"在哪儿、用谁跑、用哪份数据跑"」。

B.3 TestCase 是否必须有 revision？

必须有。理由不是"要有版本管理"，而是一个具体的正确性问题： 若 Plan 只记 case_id，那么用例被修改后，一个"没被动过"的旧计划会静默地改变行为 —— 计划本身没变、revision 没变，但跑出来的东西变了。这直接违反第一阶段已建立的 「执行即固化、历史不可回退」原则（build_plan_snapshot / build_config_snapshot 的存在理由）。

三种引用方式的比较

方式能检测"用例变了"吗旧计划是否静默漂移能否回答"当时是哪个版本"评价
① 只存 case_id否会否最差，等价于埋雷
② 存 case_id + revision能不会（可检出）能可用，但"是否漂移"要靠人去看 revision 是否落后
③ case_ref = {id, revision, fingerprint}能（自校验）不会能推荐：fingerprint 让"引用是否与当前用例一致"可一行代码判定，无需比对 revision 数字

三条与现有实现的一致性论证：

  • plans.revision 已有现成的递增惯例与 bump_revision=False 的非用户编辑旁路（db.py:360/378）→ TestCase 直接照抄。
  • 现有 plan_snapshot 把 revision 与 steps 一并冻结并算指纹（config_center.py:820-836）→ TestCase 的引用采用同样的「版本 + 指纹」双保险。
  • _h() 已存在且口径统一 → 不需要引入新的哈希约定。

B.4 Plan → TestCase 引用方式（方案 A/B/C/D 比较）

维度A：case_ref{id,rev,fp}B：case_idC：case_id + paramsD：全量展开(inline)
可复用性高高高无（复制即分叉）
历史可追溯强（含 fp）弱弱无（无法回答"这是哪个用例"）

数据库复杂度零（steps 是 JSON）零零零
前端复杂度中（要显示"与当前版本不一致"）低中低（就是现状）
改动面（见 A.3）A/B/C 都需要改 9 处透传点；D 改动面为 0
推荐：方案 A 的定稿形态 —— case_ref{id, revision, fingerprint} + override_params。
  • 不用 D：D 就是现状（inline），等于放弃"用例"这一概念本身 —— 而"同一测试被多处复用/改动要能追溯影响面"正是本次要解决的问题。
  • 不用 B：无法检出漂移。真出事时（用例改了小参数导致回归结果变化）平台无法给出任何提示。
  • 不用 C：params 一词在 step 与 case 两层含义不同（step 是"本次有效值"、case 是"定义默认值"），同名会造成长期困惑；用 override_params 命名把语义钉死。
  • D 的保留价值：作为legacy 形态永久保留（不要求迁移历史计划），见 §冻结设计 9。

合理，且是 TestCase 的核心价值所在。你给的例子（同一用例被 Plan A 覆盖 run_time、被 Plan B 覆盖 users） 正好对应当前运行库的真实情况：计划 id=10（run_time=10s）与 id=15（run_time=60s） 本质上是同一个 colyseus-bot 用例的两次不同规模执行。

推荐方案 E：把「定义指纹」与「内容指纹」拆成两个概念、两个存放位置。 这是本轮最重要的设计决定 —— 因为两者成本差 4 个数量级（纯 JSON vs 读磁盘）， 混成一个字段会导致「保存用例时被迫读几十 MB 磁盘」。

① 定义指纹 test_cases.fingerprint（保存时计算，廉价）

definition_fingerprint = _h(
    "case",
    name,                          // 进入：它会成为 jobs.name，影响报告可读标识
    engine,                        // 进入：决定 Runner 与参数口径
    json.dumps(params, sort_keys=True, ensure_ascii=False),   // 进入：规范序，避免键序差异
    int(requires_exclusive),       // 进入：影响执行机互斥
    asset_kind                     // 进入：影响资产注入与预检

// 不进入：id（身份，非定义）、description、tags、owner、enabled、revision、
//         created_at/updated_at（管理元数据，改它们不应让"同一定义"看起来变了）

② 内容指纹（执行时计算，写入 config_snapshot）

content_fingerprint = _h(
    "content",
    script_fp,        // 受控脚本文件内容 sha256（见下"哪些能算"）
    asset_dir_fp      // 受控素材目录的内容指纹（升级版 dir_fingerprint）

// 升级版目录内容指纹（替换现有只算 name+size 的实现）
dir_content_fp(path) = _h(
    basename_only(path),
    *[f"{name}:{size}:{sha256(content)[:16]}" for name in sorted(listdir(path))[:4000]]

// 单文件超过 MAX_FILE_BYTES（建议 8MB）→ 只计 name:size 并在结果里标 partial
// 不落绝对路径（沿用 path_basename_only）

哪些内容能算 / 不能算（严格受"受控登记表能否定位"约束）

对象能否定位v0.2 是否计算理由

match_eval 算法脚本不能 —— 路径来自 legacy 环境变量 PLATFORM_MATCHEVAL_SCRIPT / 项目根（matcheval_runner.py:29），不在任何受控登记表里 P1（需先补一个受控 key）顺带修掉这个遗留来源，符合"登记层唯一来源"的既有纪律
pytest 测试用例源码半能 —— 只能定位到 cwd_root 目录 v0.2 不做边界不可界定：cwd_root（如 privahigh-backend）下既有被测系统源码又有测试文件， 还可能含 .venv；全量哈希既慢又不属于平台职责 —— 这是被测系统版本控制的职责
解释器环境能 —— INTERPRETER_PROFILES 不目录极大且非"测试定义"；解释器差异已由 executor.fingerprint 覆盖
整个项目目录—明确不做你已指出：不要因为"理论上完整"就 hash 整个项目目录（性能、可重复性、Windows 路径、大目录都是坑）
性能处理：内容指纹在 PlanRun 创建时算一次（不是每个 Job 算一次）， 按受控 key 做 进程内缓存（项目已有同类做法：_MATCHEVAL_PY_CACHE，config_center.py:205）。 实测规模：23 张 1920×1080 PNG + 5 张整屏 ≈ 数十 MB，一次读取在 SSD 上远低于 1 秒。 若未来素材涨到数 GB，再引入「只在 precheck 与显式刷新时重算」的策略。

最终定义：fingerprint 到底代表什么

定义指纹 = 「这个用例作为一份定义的稳定标识」。改 name/engine/params/requires_exclusive/asset_kind 会变；改 description/tags/enabled/revision 不变。

内容指纹 = 「这一次执行所面对的被测脚本与素材内容」的标识。它不属于用例，属于这次执行的环境事实，因此放在 config_snapshot。

二者合起来才能回答：「同样的用例定义 + 同样的内容 → 结果应当可比」。

B.7 「展开 TestCase」的时机

当前 router.run_plan 的真实流程（router.py:390-426）

run_plan(pid)
 ├─ ① db.get_plan(pid)                       // plans.steps 读出来
 ├─ ② 空步骤检查（400）
 ├─ ③ validate_plan_refs(env, exec, asset)   // 仅启用的可引用
 ├─ ④ build_config_snapshot(env, exec, asset)         // ← 配置快照在此生成
 ├─ ⑤ build_plan_snapshot(plan)                       // ← 计划快照在此生成
 ├─ ⑥ db.create_run(plan_id, plan_revision, plan_snapshot)   // ← PlanRun 在此创建
 └─ ⑦ for step in plan["steps"] → _resolve_step_params → insert_job
问题答复依据
1. 何时解析 TestCase？在 ⑤ 之前，即第 ③ 与 ④ 之间插入一个 expand_cases() 必须在快照前，否则快照存的是引用而非内容
2. 在创建 PlanRun 之前还是之后？之前（严格早于第 ⑥） 展开失败必须不产生任何 PlanRun/Job；现在 ③ 的失败是 400 且不建 run，展开应沿用同一保证
3. snapshot 存引用还是展开内容？两者都存：case_ref{id,revision,fingerprint}（溯源） + step 上的有效 engine/name/params（复现） 有效值必须落在 step 原有字段上，才能让 _resolve_step_params、比较键、报告零改动
4. 用例后续被改，历史 PlanRun 是否受影响？不受影响 snapshot 已自包含；且 Job 的 params 也在创建时固化（含已解析的 cwd）， 执行阶段不再回读 test_cases 表
原则「PlanRun 创建后即使 TestCase 被修改，历史运行也不能变化」在当前结构下可成立，前提有三条： ① 展开发生在快照之前；② 固化后的 plan_snapshot / jobs.params 在执行期不再回读用例表； ③ 不新增任何"报告页实时 join test_cases"的展示逻辑（否则展示会漂移）。

B.8 legacy inline step 兼容 & 混合 Plan

形态当前是否支持需要做什么
旧 Plan（纯 inline）完全支持无需迁移。15 个计划全部是这一形态（plans.steps 皆为 4 键）
新 Plan（纯 case_ref）不支持（会 400 或被丢键）改 A.3 的 9 处 + 放宽 _plan_errors 的 engine 前置要求
混合 Plan（inline + case_ref 共存）不支持执行侧天然支持（逐 step 判断即可）；瓶颈全在 A.3 的透传点
一条可验证的强性质（建议作为验收标准）：新键仅在 case_ref 存在时写入。 这样 旧 inline step 的 JSON 与改动前逐字节相同 → 旧计划「保存后重跑」的 plan_snapshot.snapshot_fingerprint 保持不变。 若实现时对所有 step 无条件加键，会导致历史计划的指纹在"什么都没改"的情况下变化 —— 必须避免。

B.9 TestSuite 是否需要独立关系表？

不需要 test_suite_cases，也不需要 plan_cases。

直接对着执行逻辑论证 —— router.py:414：

for step in plan["steps"]:                    // ← 执行期唯一的顺序来源
    params = _resolve_step_params(step, engine, snapshot, asset)
    db.insert_job(...)
  • Suite 不参与运行期：Suite 只在编辑期展开为一段 steps 数组被写进 plan.steps。 一旦落进 Plan，运行期只认 plan["steps"] → Suite 的关联表在运行链路里完全没有读取点。
  • 引入 plan_cases 会造出第二个顺序源：steps 与 plan_cases.ordinal 谁是权威？ 必须改动上述循环 → 直接冲击已验收的执行链路。
  • test_suite_cases 与项目既有风格不符：本项目表达"有序集合"的既有做法就是 JSON 数组 （plans.steps、environment.labels、executor.allowed_runners、matcheval.algorithm 皆是）。 为 Suite 单独引一张关联表会造成两种风格并存。
  • 当前没有需求逼出关联表：没有参数化、没有 DAG、没有跨 Suite 复用查询、没有"某用例被哪些 Suite 引用"的运维诉求。

→ 明确建议暂缓：不因为"数据库规范化"就自动加 association table。若未来出现「反查某用例被哪些 Suite 引用」的硬需求，再引关联表也不迟（届时是纯新增，无破坏性）。

5. TestCase revision 规则

事件处理依据 / 类比
创建revision = 1，同时计算 fingerprint同 db.create_plan（db.py:355 写死 revision=1）
修改定义字段
（name/engine/params/requires_exclusive/asset_kind/description）		 revision += 1，并重算 fingerprint 同 update_plan(bump_revision=True)（db.py:378）
切换 enabled不递增 revision 启停是"可用性开关"而非"定义"；它也不进 fingerprint —— 若递增会让"停用一下"污染版本历史
改 tags / owner不递增（P1 细化项）管理元数据，不进指纹

Plan 引用存 {id, revision, fingerprint} 三元组见 §4

历史运行不受任何影响执行期不回读 test_cases；Job params 已固化

6. override 规则

规则内容
允许覆盖_STEP_PARAM_KEYS[engine] 内的键（含用例未声明但属白名单的键）；以及 step 层的 name、requires_exclusive
禁止覆盖engine（天然不在白名单内）；asset_source_id（内部兜底注入键，router.py:434 会 pop，显式拒绝）； 白名单外的任何键；绝对路径 / 盘符 / .. / shell 元字符 / .exe（既有限制全部继承）
合并语义浅合并 merged = {**case.params, **override_params}（override 优先）；不做深合并（args 等数组整体替换）
校验对 merged 整体调用一次 validate_step_params(engine, merged)；再额外拒绝 asset_source_id； 执行期继续由 _resolve_step_params 做受控解析
校验失败返回HTTP 400，正文为「；」拼接的逐条错误，沿用现有格式（如 steps[1] [locust] 不接受的参数键：'foo'（只允许 [...]））

7. fingerprint 规则（最终定义）

定义指纹（TestCase.fingerprint，保存时计算）
fingerprint = _h("case", name, engine,
                 json.dumps(params, sort_keys=True, ensure_ascii=False),
                 int(requires_exclusive), asset_kind)

内容指纹（执行时计算，写入 Job.config_snapshot）
content_fingerprint = _h("content", script_fp, asset_dir_fp)
进入定义指纹不进入定义指纹
name · engine · params（规范序） · requires_exclusive · asset_kind id · description · tags · owner · enabled · revision · created_at · updated_at
进入内容指纹不进入内容指纹
受控 locust 场景脚本文件内容（LOCUST_SCENARIOS[key]）
受控素材目录内容（TPL_DIRS / SCENES_DIRS，升级版 dir_content_fp）		 整个项目目录（明确拒绝）· WORKDIR_ROOTS 工作目录（被测源码，边界不可界定）· 解释器环境目录 · 单文件 > 8MB 的内容（降级为 name:size 并标 partial）

计算时机与成本：定义指纹=保存时（纯 JSON，微秒级）；内容指纹=PlanRun 创建时算一次（数十 MB，按受控 key 进程内缓存）。

Part E · 最终结论

可以冻结的设计：

  • TestCase 的身份定位：定义层实体，不含执行态、不绑定环境/执行机/资产源。
  • TestCase 字段集（13 列，见 §2），含 requires_exclusive 与 asset_kind，不含 notes/entry/expected_result/status。
  • revision 机制（§5）：照抄 plans.revision；内容变更 +1，enabled 切换不 +1；支持 bump_revision=False。
  • Plan step 结构（§4）：case_ref{id,revision,fingerprint} + override_params，与 legacy inline 二选一、可在同一 Plan 内混合。
  • override 规则（§6）：白名单内、浅合并、对 merged 整体校验、engine 与 asset_source_id 禁止覆盖、失败返回 400。
  • 展开时机（B.7）：get_plan 之后、build_plan_snapshot 之前；展开失败不产生 PlanRun/Job。
  • snapshot 结构（§8）：step 保留有效值 + 附加 case_ref/override_params；下游零改动。
  • TestSuite 范围（§10）：只做表 + CRUD + 页面 + 编辑期展开；不做关联表与一切高级能力。
  • 兼容策略（§9）：历史 Plan 不迁移；旧步骤 JSON 与指纹逐字节不变。

编码前必须先解决的问题：

  1. P0-2：A.3 的 9 处透传点必须作为一次原子改动完成（含前端与 db.create_plan），并加"往返保真"验证 —— 否则功能会以"静默丢键"的形式假成功。
  2. P0-1：内容指纹必须与 TestCase 同批交付。它是本轮的起因，也是"用例"这个概念能否成立的前提： 没有它，平台只能证明"定义相同"，不能证明"跑的东西相同"。
  3. 一个待你拍板的取舍：pytest 的内容指纹是否纳入 v0.2。 本设计建议不纳入（工作目录边界不可界定，属被测系统版本控制职责）—— 但这意味着 pytest 用例仍然存在"来源可信度"缺口。若你希望覆盖它，需要先定义"哪些文件算受控测试内容"（例如只哈希 cwd_root 下 tests/**/*.py）， 这会让 v0.2 范围明显变大。
