1. 当前架构复盘

1.1 当前真实链路（无 TestCase 概念）

Environment协议 / host:port / 凭据引用
→ 被引用 →

→ run →

→ 1:N →

→ 1:1 →

绿=配置层；青=执行与结果层（已冻结）。当前 不存在任何「测试用例」实体： 「一个测试」目前只是 plans.steps[] 里的一个内联 JSON 对象。

1.2 关键事实：步骤「身份」目前是隐式的

运行库实测（只读）——同一 jobs.name（步骤名）被跨计划重复使用：

jobs.name 分布： timeout 5 · slow 4 · retry 4 · colyseus-bot 4 · pass 3 · fail 3
                ui-wait 2 · ui-pass 2 · privahigh-visual 2 · privahigh-functional 1

更关键的是 同名 ≠ 同参数：计划 id=10（Locust-Colyseus，run_time=10s）与 计划 id=15（Locust-Colyseus 完整局，run_time=60s）用的是同一个步骤名 colyseus-bot， 但参数完全不同；计划 id=13 与 id=14 的 privahigh-visual 则参数一致。

→ 今天「这是不是同一个测试」只能靠命名约定，平台无法回答「这个测试被哪些计划用了」 「改了它会影响哪些历史/未来运行」。这正是 TestCase 要解决的核心问题。

1.3 建议的目标关系（未来态，本文只给设计）

TestCase测试定义 + revision
TestSuite有序用例集合 + revision
→ 被引用（不复制） →
Plan引用 + 覆盖参数 + 顺序
→ run →
PlanRun快照中展开为自包含定义
→ 1:N →
Job语义不变
→ 1:1 →
Report语义不变

紫虚线=新增（仅定义层）；青=保持不变。扩展点只有一处：Plan 的步骤来源从「内联」变为「引用 + 展开」。

2.2 逐项回答审计问题

问题结论（含依据）
Plan ↔ PlanRunplan_runs.plan_id → plans.id（逻辑外键，1:N）。 PlanRun 额外冻结 plan_revision 与 plan_snapshot（db.py:186-191 迁移补列）。 Plan 可变、PlanRun 不可变。
PlanRun ↔ Jobjobs.plan_run_id → plan_runs.id（1:N，有索引 idx_jobs_run）。 Job 另冗余 jobs.plan_id（省一次 JOIN）。 Job 还复制了 plan 的 environment_id/executor_id 并固化 config_snapshot。
Job ↔ Reportreports.job_id UNIQUE → 严格 1:1；report_index.job_id UNIQUE → 1:1 读模型。 scheduler 在 _run_job 里先 write_report 落盘、再 save_report 入库、最后 _index_report 派生索引 （scheduler.py:221-242）。
是否已有可复用的「测试资产」概念？有，但语义不同。 asset_sources 是数据资产（素材/场景/真值/压测脚本 key），不是「测试用例」。 真正的「用例雏形」是 plans.steps[] 的内联对象 {engine,name,requires_exclusive,params} （domain.py:127-132）—— 它匿名、内联、无独立版本、不可跨计划复用。
可支持未来 TestCase 的字段模式① revision + created_at/updated_at（plans 已有，update_plan(bump_revision=True) 为既有惯例）； ② enabled 启停位（三张配置表已有，配 /toggle 路由）； ③ owner；④ description/notes；⑤「受控 key 白名单 + 后端校验」的整套模式（validate_*_input）。
不能复用的字段jobs.* 的执行态字段（status/exit_code/log_path/report_path/started_at/ended_at/attempt/retry_of）、 plan_runs.plan_snapshot（计划级，不是用例级）、report_index.*（结果读模型）—— 这些属于「执行」而非「定义」，混入会破坏 domain.py:8-18 已冻结的状态机语义。

3.2 revision 与两层快照如何工作

用户编辑 Plan → update_plan(bump_revision=True) → plans.revision + 1        (db.py:360)
预置 / 回填   → update_plan(bump_revision=False) → revision 不变

执行 Plan → router.run_plan()                                              (router.py:390-426)
   ├─ plan_snapshot   = build_plan_snapshot(plan)         → 存入 plan_runs.plan_snapshot
   ├─ config_snapshot = build_config_snapshot(env,ex,asset) → 存入每个 jobs.config_snapshot
   ├─ create_run(plan_revision=plan["revision"], plan_snapshot=...)
   └─ for step in plan["steps"]: 逐条 insert_job(params=_resolve_step_params(...))

两个快照的职责分离（config_center.py:805-837 与 :727-767）：

快照挂在谁身上内容指纹哈希输入
plan_snapshotplan_runs（每次执行一份） name / description / revision / fail_fast / owner / 三个引用 ID / steps 全量展开 _h("plan", plan_id, revision, steps_json, env_id, exec_id, asset_id, fail_fast) —— 含 plan_id
config_snapshotjobs（每个 Job 一份） environment（脱敏 + fingerprint）/ executor（脱敏 + fingerprint）/ asset_source（refs + fingerprint） _h(env_fp, exec_fp, asset_fp)
⚠️ 两个快照都只对「受控 key / ID」取哈希，不含被测脚本与资产的内容： asset_fingerprint() 只哈希 dataset_ref/tpl_ref/scenes_ref/...（config_center.py:385-391）。 目录内容指纹 dir_fingerprint() 虽然存在（:397-412），但只在 precheck_asset_source 里算、从不写进快照。 → 详见 §7 与附录 A 问题 ①。

3.3 未来最小变化

结论：Plan 表结构完全不需要改，只需改变 steps[i] 的内容语义：

// 现状：内联（匿名用例）
{"engine":"pytest","name":"privahigh-functional","requires_exclusive":false,
 "params":{"cwd_root":"privahigh-backend","args":["tests/","-o","addopts=","--tb=short"],"timeout_sec":300}}

// 未来：引用（命名用例）—— 保留 name/params 作为「本计划覆盖值」
{"case_ref":{"id":12,"revision":3,"fingerprint":"ab12cd34ef56"},
 "name":"privahigh-functional",            // 展示名，可覆盖
 "requires_exclusive":false,
 "params":{"timeout_sec":600}}             // 仅覆盖差异项；其余继承用例定义

为保证历史可复现，执行时把用例定义展开成完整步骤再进快照（见 §7）， 因此 plan_snapshot 仍是自包含的，现有不可变机制一行不改。

4. TestCase 最小模型建议

只给模型，不建表。「必须」= 缺了就无法表达一个可执行、可复现、可比较的用例； 「可选」= 有明确用途但 v0.2 可延后；「不该有」= 与现有架构冲突或造成双源。
字段类型职责是否必须依据 / 理由
idINTEGER PK AUTOINCREMENT稳定身份，供 Plan 引用必须与全库主键风格一致

requires_exclusiveINTEGER DEFAULT 0是否需要执行机独占必须已在 PlanStep 上存在（domain.py:131），语义属用例
timeout_secINTEGER DEFAULT 300默认超时（Plan 可覆盖）必须现状 params.timeout_sec 被复制进 jobs.timeout_sec（router.py:421）
revisionINTEGER DEFAULT 1定义版本必须完全照搬 plans.revision 的既有惯例

ownerTEXT DEFAULT 'local'归属建议plans.owner 已有同名字段
tagsTEXT DEFAULT '[]'标签（过滤/分组）可选 P1与 environments.labels 同风格（_json_list 已有工具）
expected_resultTEXT DEFAULT ''期望结果声明v0.2 不该有三引擎判定口径完全不同（见 §6），强行统一会造出无法校验的字段；判定应由 Runner 产出
entry—「入口」单一字段不该有pytest 是相对选择器、locust 是场景 key、matcheval 是 dataset key。统一字段必然扭曲语义，应由 params 承载
executor_id—绑定执行机不该有与 plans.executor_id 形成双源；解释器实际由 engine 决定（_ENGINE_DEPS）
environment_id—绑定环境不该有同一用例应可在不同环境复用（比较/回归的前提）；环境属计划或执行级
asset_source_id—绑定资产源不该有同一用例换数据集/场景是常见变化；应改为声明资产需求种类（见下）
status（执行态）—最近一次执行结果不该有执行态属 Job；用例表若存状态会成为第二个事实源。若要"最近结果"，应由 report_index 派生
asset_kind（新增语义）TEXT DEFAULT ''声明「需要哪一类受控资产」（matcheval/locust/空）可选让预检能提前提示「本用例需要 dataset 但计划未给」；声明种类而非绑定 ID
关于「TestCase 是否应绑定 Executor / Environment / AssetSource」的结论：都不应绑定。
  • Executor：现有 executors.allowed_runners + _ENGINE_DEPS（pytest→pytest、locust→locust、matcheval→cv2/numpy） 已经能表达「哪个引擎能在哪台执行机跑」，用例再绑一次是冗余且会打架。
  • Environment：Plan 已绑（plans.environment_id），Job 从 plan 复制（router.py:420）。 用例若也绑，同一用例换环境就必须改用例 → 破坏可复用性。
  • AssetSource：Plan 已绑。用例只应声明种类需求，具体数据集由计划决定 —— 这与现状 _asset_key_for(asset, engine)（router.py:448-453）的注入逻辑天然吻合。

v0.2 最小 TestSuite 应该做到什么

  • 就是「一个有序的 TestCase 引用集合 + 名称 + 版本」—— 不承担调度、不承担环境绑定。
  • 在 Plan Editor 里可作为一次插入多个步骤的来源（相当于「批量粘贴步骤」的受控版本）。
  • 是否引入 test_suite_cases 表：推迟。理由 —— 现有 plans.steps 已经用 JSON 存有序集合， 再为 Suite 单独引一张关联表会造成两种风格并存；且 v0.2 无「反查某用例被哪些 Suite 引用」的硬需求。

结论：可以统一「用例的元数据与容器」，不能统一「用例的执行入口与结果口径」。 这三组差异不是历史包袱，而是引擎本质：validate_step_params（config_center.py:868-917）已经按引擎分派白名单， engine_compare_key（report_center.py:41-83）已经按引擎生成比较键。 因此 TestCase 的 params 必须继续走引擎白名单校验，绝不能抽象成一个通用 entry 字段。

7.2 关键设计：展开必须在快照之前

执行时（router.run_plan 现状 → 未来）：

12. 风险

#风险依据（当前代码事实）影响缓解
R1TestCase 与 Runner 强耦合 三引擎参数集与结果口径本质不同（§6.2）；_STEP_PARAM_KEYS 已按引擎分派 若强行统一 entry，会造出无法校验的字段并污染 compare_key 接受分引擎；用例表只统一元数据 + params 整体走引擎白名单
R2TestCase 与环境/执行机耦合 Plan 已持有三个引用 ID（plans.environment_id/executor_id/asset_source_id） 用例上再绑 → 双源冲突、用例不可跨环境复用 用例只声明 asset_kind 需求；环境/执行机留在 Plan
R3快照过大 plan_snapshot 存的是 steps 全量 JSON（现状已如此） 若未来引入参数化/矩阵展开，快照可能膨胀到 MB 级，拖慢 plan_runs 读写 v0.2 不引入参数化；若要引入，改为「快照存用例 revision + 受控指纹，正文单独落文件」
R4版本引用混乱 build_plan_snapshot 指纹含 plan_id（config_center.py:832-836）→ 草稿态与已保存态指纹不可比（已有实际踩坑：edb4439a8bd4 vs 58e2bb45cf93） 引入用例指纹后，「指纹比较」的坑会成倍增加（用例指纹 / 计划指纹 / 配置指纹三个口径） 明确并文档化三种指纹各自的可比范围；凡比较一律比内容，不比数字
R5三引擎抽象过度 ENGINES 是元组常量、RUNNERS 是固定字典（executors/__init__.py） 为「泛化」而把 Runner 抽象成插件体系，会超出 MVP 边界且无实际需求 v0.2 维持 3 个引擎不变；不加新引擎
R6数据库迁移风险 全库无外键；迁移是「启动时 PRAGMA 探测 + 逐列 ALTER」（db.py:151-193），且每次启动都会跑 新增表/列若写错 DDL 或顺序，会影响真实运行库（当前 25 runs / 30 jobs 的历史） 严格遵守「只 ADD COLUMN / 只 CREATE IF NOT EXISTS」；先在隔离临时库验证再对运行库启动（项目已有此惯例）
R7引用完整性无数据库保障 0 个 FOREIGN KEY；validate_plan_refs 只在应用层查（config_center.py:921-941） 若某用例被停用/删除，已引用它的 Plan 会在执行时才报错 沿用现状：用例不做物理删除（与「不实现删除计划」一致），只 enabled=0；执行前 validate_plan_refs 扩展为同时校验用例引用
R8历史语义漂移（内容指纹缺失） asset_fingerprint 只哈希 key；dir_fingerprint 不入快照。实测三轮 plan_snapshot 指纹相同 96885f59a1b6 「同用例同结果」的承诺无法兑现；A/B 对比可能比较了不同的被测代码 列为 P0（§10 第 6 项）
