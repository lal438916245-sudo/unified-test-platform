4. /health 怎么实现

def build_app(static_dir: str) -> FastAPI:
    app = FastAPI(title="统一游戏测试平台 MVP")

    @app.get("/health", include_in_schema=False)
    def _health() -> dict[str, str]:
        """最小存活探针：只证明 HTTP 服务已监听。严格零副作用。"""
        return {"status": "ok"}

    app.include_router(api_router)          # 业务 API 仍在 /api/*
    ...
  • 刻意的设计选择：挂在 app 根路径，不经业务 router（router = APIRouter(prefix="/api")）。这样"服务已起来"与"配置/资产是否就绪"彻底解耦 —— 它不继承 /api 的依赖链。
  • 零副作用：不访问 DB、不创建 PlanRun/Job、不读被测资产、不依赖 Environment/Executor/AssetSource，也不依赖 Locust/MatchEval。测试里有一条专门的断言：给 app 设了 db_path 后调 /health，该 sqlite 文件必须仍不存在。
  • 配套测试 backend/tests/test_health.py（4 条）：① 200 + 载荷严格等于 {"status":"ok"}；② 在根路径而非 /api/health（后者必须 404）；③ 零副作用（不创建 DB 文件）；④ 未配置 db_path 也可用（证明不依赖 DB/调度器/资产）。
  • 按要求只做 /health：没有 /ready、/metrics、Prometheus、tracing、auth、dashboard。

  3. 跑测试：$LASTEXITCODE -ne 0 即抛出。

身份自证（你 §11 特别强调的那件事）

2026-10-01 曾因"只看端口 UP、把遗留实例误认成自己启动的实例"而把 9 条 PlanRun 写进真实库。为此 L1 用五重、互相独立的证据链，而不是单一信号：

  1. 启动前端口不可达 → 起完后可达 ⇒ 这个监听者只可能是本次新起的进程。
  2. 子进程自己 stdout 声明了它绑定的 http://127.0.0.1:<port>、数据库:、数据目录: —— 读它的原话，不靠推测。（首版这里踩了坑：子进程 stdout 被块缓冲，横幅滞留在缓冲区读不到；已在子进程环境强制 PYTHONUNBUFFERED=1 解决。）
  3. OS 报告的该 PID 命令行同时含本次 run.py、本次端口、本次临时数据目录。
  4. 进程存活用 Windows API（OpenProcess + GetExitCodeProcess==STILL_ACTIVE）判定 —— 不用 tasklist（本机 tasklist 与 netstat 一样会静默返回空）。
  5. 进程退出后端口再次不可达 ⇒ 闭合证明"监听者确为本次进程"。

再叠加一条"写入去向"的硬证据：执行后临时库有本次记录、真实库计数不变。

7. CI workflow 如何执行

文件：仓库根 = platform/，因此路径是 platform/.github/workflows/platform-ci.yml。

name: Platform CI (L0 + L1)
on:
  workflow_dispatch:              # 第一阶段只开手动触发，不加 push / pull_request
concurrency:
  group: platform-ci              # 平台是 SQLite + 进程内 scheduler + executor_locks，
  cancel-in-progress: false       # 存在全局串行约束 → 整个 workflow 串行化
permissions:
  contents: read
env:
  PYTHON_EXE: ${{ vars.PLATFORM_CI_PYTHON || 'python' }}
  NO_PROXY: 127.0.0.1,localhost   # 本机有 http_proxy，否则 127.0.0.1 会被送去代理(502)
jobs:
  l0-unit:            runs-on: [self-hosted, Windows]   # 环境自检 → 真实库指纹(前) → pytest → 校验未写真实库
  l1-platform-smoke:  runs-on: [self-hosted, Windows]   # needs: l0-unit
                      # 指纹(前) → python _ci/l1_smoke.py → 校验未写真实库
                      # → 残留进程检查(always) → 上传 _ci_out/ 为 artifact l1-smoke-logs(always)

几个刻意的选择

选择理由
runs-on: [self-hosted, Windows]平台依赖 Windows 本机 Python 与受控本地路径；托管 runner 看不到这些，跑不了 L1
只开 workflow_dispatch按你的要求：等它在当前 runner 上稳定通过后，再单独评估是否加 push/pull_request
workflow 级 concurrency同一平台同时只允许一个实例；不通过 Worker/队列解决
残留进程检查只匹配"run.py 且带 --data-dir"CI 启动的平台必然带 --data-dir；这样不会误伤开发机自己起的 python backend/run.py --no-browser（否则该 job 会被无关进程搞红）
两个 job 各自记录真实库指纹并前后比对把"CI 不得写真实库"做成 workflow 级断言，而不只是脚本内部的自我承诺
日志上传用 if: always()失败时更需要现场

YAML 已做结构校验：解析通过，并断言 on 仅 workflow_dispatch、两个 job 均为 self-hosted + Windows、jobs 中不含 ubuntu、concurrency.group == platform-ci 且 cancel-in-progress == false、l1 依赖 l0。
