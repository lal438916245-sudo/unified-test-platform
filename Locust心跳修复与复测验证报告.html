3. 根因更正：是心跳 ping/pong，不是「补丁积压」

更正上一轮结论。 我在《Locust 连接约 7 秒被中止-根因定位》中判断 「客户端只发不读 → 房间状态补丁在接收缓冲积压 → 连接被中止」。 该判断被本轮实测推翻：入站数据帧实际只有 1 帧，根本没有可供积压的补丁。

实测：房间里其实几乎没有入站流量

6 秒窗口内：发包 60 次，入站 1 帧 / 827 字节（首字节 10 = JOIN_ROOM 全量状态）
入站帧首字节分布: {10: 1}
入站速率: 0.13 KB/s，0.2 帧/s
（同一现象在 Locust 三轮日志中一致复现：每轮「排空入站 1 帧 / 827 字节」）

即 MMORoom.onCreate 虽设了 setPatchRate(50) 与 setSimulationInterval，但该客户端在整个对局期间并未收到周期性状态补丁。

真正机制：Colyseus 传输层的 ping / pingMaxRetries 心跳

证据来自安装包源码 colyseus/esm/transport/WebSocket/WebSocketTransport.mjs：

this.pingIntervalMS  = options.pingInterval  ?? 3000;   // 默认 3s
this.pingMaxRetries  = options.pingMaxRetries ?? 2;      // 默认 2 次

function heartbeat() { this.pingCount = 0; }              // ← 只有收到 pong 才归零

autoTerminateUnresponsiveClients(pingInterval, pingMaxRetries) {
  this.pingInterval = setInterval(() => {
    this.wss.clients.forEach((client) => {
      if (client.pingCount >= pingMaxRetries) {
        return client.terminate();                        // ← 主动踢连接
      }
      client.pingCount++;
      client.ping(noop);                                  // ← 发 WS 控制帧 ping
    });
  }, pingInterval);
}

与实测吻合：改前「只发不读」的独立探针在 9.15s 后抛 WinError 10053；改前压测 9 条连接平均存活约 7.1s（含连接建立偏移）。 而 ping 是 WebSocket 控制帧，不是数据帧 —— 客户端只有在调用 recv() 时才会读到它，由 websocket-client 内部自动回 pong， 服务端 pingCount 才归零。

所以修复起作用的原因：新增的 drain_inbound() 让客户端周期性调用 recv() → 读到服务端 ping → 自动回 pong → pingCount 归零 → 不再被 terminate()。它并非在清空缓冲积压（本就没有积压）。 这也解释了「排空只读到 1 帧却仍让连接活了下来」这个看似矛盾的现象。

顺带修正：上一轮「C 组空等 11s 仍存活」的对照并不成立

改前那组「不发不读、静默 11s 后首次发送成功」曾被当作反证。实际上 TCP 发送缓冲 会先接收写入、RST 稍后才反映到下一次发送，因此单次成功发送不能证明连接仍在。 该组不构成有效对照，已被本轮的 3s×3 算术 + 9.15s 实测取代。

4. 改动安全性论证（为什么非阻塞读取不会读坏帧）

  • 不会死循环：websocket/_socket.recv() 在 sock.gettimeout() == 0 时直接调用 sock.recv()，无数据抛 BlockingIOError；该异常不被 except TimeoutError / except socket.timeout 捕获 → 直接向上传播，不会落进 select 分支返回 b""（那条路径才是死循环风险）。
  • 不会读坏帧：frame_buffer 跨调用保留半帧状态 —— 残量留在 recv_buffer，header/length 只在整帧组装完成后 才 clear()，故某次 recv 因无数据中断后，下次调用可无缝续读。
  • 不影响发包节奏：finally 恢复原超时（10s）， send 语义不变；time.sleep(0.1) 与 random.randint(10,20) 均未改动。
  • 不修改被测对象：未改服务端的 pingInterval / pingMaxRetries / patchRate —— 避免「改被测对象以迁就测试」。

7. 仍然存在的限制

  • 未跑第 3 轮及以后：第 3 轮进入 30s 登录冷却等待后被 run_time=60s 正常截断。要覆盖第 3 轮需 run_time ≥ 90s。
  • 入站流量极低：本房间对客户端几乎不下发数据（6s 内 1 帧），所以该脚本 实际测的是「高频写入吞吐」，不是「收发双向负载」。若需要真实双向压力， 需另写会消费状态的场景（本仓库 Server/loadtest/ 用的是官方 colyseus-loadtest）。
  • 并发规模仍为 3 用户：属保守链路验证，不足以反映容量拐点。

8. 结论

修复有效、可重复，且根因已从源码与实测两端闭合：

  • 被测脚本缺陷：对局循环只 send 不 recv → 无法应答 Colyseus 的 WS 层 ping → 约 9s 后被服务端 terminate()；且异常未进统计， 使其被「0 失败」掩盖。
  • 平台无责：正确拉起 Locust、正确归档产物、正确建立报告索引。
  • 服务端无责：心跳踢掉不响应的客户端是正常保护行为。
  • 修复方式：仅改被测脚本（+80/−2），未碰服务端、未碰平台代码、未改并发与时长参数。
