压测连接约 7 秒被中止 · 根因定位报告Colyseus-Storm Bot ↔ MMORoom · 2026-10-01

问题：60s 完整局压测（PlanRun#23）中，9 条 WebSocket 连接逐条在约 6~9 秒被中止（WinError 10053）， 每轮对局（脚本设定 10~20s）都没跑完，游戏结束 恒为 0 次。 本报告用 4 组对照实验 + 源码阅读定位成因。未改动任何被测资产（探针为临时文件，已删除）。

A 组 9.15s 死F 组（5 倍速率）7.31s 死 C 组（不发不读）>11s 存活结论：只发不读

结论

成因是"只发不读"：压测脚本在对局循环里只 ws.send()、从不读取任何入站数据。 服务端房间按 patchRate 持续把状态补丁回推给客户端（含发送者自己），而客户端的接收缓冲无人消费 → 连接在 约 6~9 秒被中止；客户端下一次 send 即抛 WinError 10053（本机侧连接已被中止）。
只要不读，连接就活不过 ~9 秒 → 永远不可能跑完一局（10~20s）。这与 run_time、与关停、与载荷格式都无关。

2. 由实验结果排除掉的解释

曾经的解释判决依据
「run_time 到点关停把连接切断」 排除 A/F 两组都在 12s 窗口内自然死亡（9.15s / 7.31s），远早于窗口结束；60s 压测里也是每 7 秒左右死一条。
「载荷格式/事件 id 不匹配，服务端报错断开」 排除 探针复刻同一帧格式；源码核对：xPos/yPos/zPos 在 RoomState.ts:10-12 均为 @type("number")； networkedUsers key = client.id（MMORoom.ts:119/282）与 seat sessionId 一致； :170-194 未命中只 logger.info 后 return，不抛错。
「服务端心跳 ping 超时踢人」 排除 Colyseus transport 确实有该机制（WebSocketTransport.mjs:25-30 默认 pingInterval=3000、pingMaxRetries=2， :55-71 达到阈值即 client.terminate()），但 C 组"不发不读"静默 11 秒后连接依然存活 —— 若单纯是心跳超时，C 组也应在 ~9s 被杀。
「客户端发送过快/过密」 排除 F 组发包速率是 A 组的 5 倍，死亡时间只从 9.15s 变到 7.31s（不同比）—— 说明死亡时间由服务端回推的节奏决定，而不是由客户端发包量决定。

3. 机制（时间线）

t=0        客户端连上房间 → 服务端下发 1 帧全量状态 ROOM_STATE（实测 827 B）
t≥0        客户端每 0.1s 发一次 entityUpdate（改了 xPos/yPos/zPos → 房间状态变"脏"）
t≥0        服务端按 patchRate 持续向房间内所有客户端广播状态补丁（**包括发送者自己**）
           客户端从不 recv → 这些补丁全部堆在客户端接收缓冲里，无人消费
t≈6~9s     缓冲积压到临界 → 连接被中止（服务端写失败 / 本机侧 RST）
t≈6~9s     客户端下一次 send → ConnectionAbortedError [WinError 10053]

关键对照：C 组"不发不读"时房间状态不变 → 服务端没有补丁可推 → 无积压 → 连接自然活着。 反过来只要一开始发包，房间状态就一直"脏"，补丁就以固定节奏（约 20 次/秒）灌下来 —— 这解释了 为什么把发包速率提高 5 倍，死亡时间几乎不变。

旁证：本仓库 Server/loadtest/ 用的是官方 colyseus-loadtest 客户端（会正常消费状态）， 行为与"裸 socket 只写"不同；Unity 真实客户端同样会读取状态。

侧判定说明
平台无责按受控参数正确拉起 Locust、正确归档 report.json 与 5 个产物、Report Center 正确索引。任务本身"执行成功"。
被测服务端行为正常正常广播状态、正常心跳；客户端不读数据导致连接不可用，属客户端侧问题。

5. 修复建议（本轮未执行，需你授权）

  1. 最小修复（推荐）：在对局循环里加非阻塞排空 —— 
    ws.settimeout(0)                 # 或 select 判可读
try:
    while True: ws.recv()        # websocket-client 在此过程中会自动回 pong
except Exception:
    pass
    预期效果：连接可长期存活 → 单局 10~20s 能跑完 → 日志出现 [Round N] 游戏结束。
  2. 配套（强烈建议）：把对局阶段的异常接入 events.request.fire(request_type="WebSocket", name="[3] Gameplay", …, exception=e)， 否则类似本次的 9 次连接中止永远不会出现在失败统计里。
  3. 不建议改被测服务端的 pingInterval/pingMaxRetries/patchRate —— 那会改变被测系统行为，属"改被测对象以迁就测试"，会污染结论。
  4. 平台侧无需改动。
