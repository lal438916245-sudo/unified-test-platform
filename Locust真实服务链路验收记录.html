5. 最终根因记录

根因：Colyseus WebSocket 心跳机制要求客户端持续读取控制帧；原 Locust 场景只发送、不读取， 导致客户端未及时处理 ping/pong；通过对局循环增加非阻塞 recv 排空，使 websocket-client 能处理心跳。

5.1 服务端机制（源码依据）

文件：colyseus-game-client\Server\node_modules\colyseus\esm\transport\WebSocket\WebSocketTransport.mjs

this.pingIntervalMS  = options.pingInterval  ?? 3000;   // 每 3s 发一次 WS 控制帧 ping
this.pingMaxRetries  = options.pingMaxRetries ?? 2;     // 连续 2 次未响应即踢

function heartbeat() { this.pingCount = 0; }            // ← 只有收到 pong 才归零
rawClient.on('pong', heartbeat);

autoTerminateUnresponsiveClients(pingInterval, pingMaxRetries) {
  this.pingInterval = setInterval(() => {
    this.wss.clients.forEach((client) => {
      if (client.pingCount >= pingMaxRetries) {
        return client.terminate();                      // ← 主动关闭连接
      }
      client.pingCount++;
      client.ping(noop);                                // ← 发送控制帧 ping
    });
  }, pingInterval);
}

与实测吻合：修复前独立探针「只发不读」在 9.15s 抛 WinError 10053； 修复前压测 9 条连接平均约 7.1s 中止（含连接建立偏移）。

5.2 客户端修复机制

ping 是 WebSocket 控制帧，不是数据帧。客户端只有在调用 recv() 时才会读到它， 并由 websocket-client 在 recv_data_frame() 内部自动回 pong，服务端 pingCount 才归零。 原场景在对局循环中只 ws.send() 而从不 recv()， 因此 pingCount 一路累积到 2 → 约 9 秒后被服务端 terminate()。

一处此前的错误归因，已在本记录中更正： 早前曾判断为「客户端只发不读 → 房间状态补丁在接收缓冲积压 → 连接被中止」。 实测**推翻**该结论 —— 6 秒窗口内发包 60 次，入站仅 1 帧 / 827 字节（首字节 10 = JOIN_ROOM 全量状态）， 此后并无周期性状态补丁，不存在可供积压的数据。这也解释了「排空只读到 1 帧，却仍让连接活了下来」这一现象： 排空带来的收益是维持心跳，而非清空缓冲。
