# 异机完整验收操作手册

版本：2026-10-18 · 适用：Windows 64 位、本机独立部署 · 配套材料：检查清单、示例项目、用例与计划 JSON。

## 1. 这次要证明什么

在另一台真实电脑上，把平台和测试项目放在自行选择的目录，通过网页登记资源、导入自己的定义，完成预检、执行、日志、报告及重启恢复，整个过程不修改平台源码。

按两个层次操作：**先完成随文示例的成功 / 故意失败校准，再完成目标电脑真实项目的测试。** 示例通过只说明基础链路成立，真实项目未跑通时不能填写“异机完整验收通过”。UI / 压测 / 视觉按实际需要勾选验收范围；未选择的引擎写“不适用及原因”，不要写通过。

本轮由目标电脑自己运行平台和测试进程。请在目标电脑浏览器访问它自己的 `127.0.0.1`；这里不验收远程执行机、自动启动 Unity、自动复位或多用户登录。

## 2. 出发前准备与记录

把以下材料复制到目标电脑。安装包与本文操作包是两份文件，不需要复制当前平台的整个工作区。

| 材料 | 用途 / 要求 |
|---|---|
| `test-platform-windows.zip` | 在线安装版；需要目标电脑已有 64 位 Python 3.11+，安装时可以访问包源 |
| `test-platform-windows-py313-offline.zip` | 二选一；带 Windows x64 / CPython 3.13 核心依赖，仍需先安装 Python 3.13 |
| `异机完整验收操作包.zip` | 本手册、可填写检查清单、示例项目和示例 JSON；不含 Python 或平台安装包 |
| 自己的测试项目、资产、依赖清单 | 真实业务验收使用；JSON 不携带脚本、图片、虚拟环境或业务数据库 |
| 可选：源平台导出的定义 JSON | 已有用例 / 套件 / 计划需要迁移时准备，也可用本文自有定义示例 |

记录电脑名称、Windows / Python 版本、安装包名与 SHA256、平台目录、项目目录、数据目录、端口及本轮要验收的引擎。在线 / 离线安装任选一种，不需要各装一次。

下面统一用一套**示例路径**。请换成目标电脑实际存在的路径，不要创建或依赖源电脑的 `F:\测试平台`、`F:\Anaconda3`。

```text
平台目录：D:\工具\异机测试平台\platform
Python：  C:\Python313\python.exe
项目目录：E:\QA\目标机 验收项目
平台地址：http://127.0.0.1:8000
```

解压平台包后本身包含一层 `platform/`。以下所有安装、启动命令都在**含 install.bat、start.bat、backend 的那层目录**运行。记录实际解压路径，不必与上面的示例逐字一致。

## 3. 安装与启动

### 3.1 确认 Python

在目标电脑 PowerShell 执行；路径按实际替换：

```powershell
& 'C:\Python313\python.exe' -c "import sys,struct; print(sys.executable); print(sys.version); print(struct.calcsize('P')*8)"
```

最后一行应为 `64`，版本应满足安装要求。安装器创建平台自己的 `.venv`；无需复制源电脑虚拟环境，也无需执行 `conda activate`。

### 3.2 在线安装（二选一）

```powershell
Set-Location -LiteralPath 'D:\工具\异机测试平台\platform'
.\install.bat -PythonExe 'C:\Python313\python.exe'
```

看到 `Core dependencies ready` 和 `Installation complete` 后继续。如果 Python 已正确加入 PATH，也可以直接双击 `install.bat`。命令中的路径含空格时，建议用双引号包住路径。

### 3.3 离线安装（二选一）

使用带 `wheelhouse` 的 Python 3.13 离线包：

```powershell
Set-Location -LiteralPath 'D:\工具\异机测试平台\platform'
.\install.bat -Offline -PythonExe 'C:\Python313\python.exe'
```

随包只带核心服务与 pytest 依赖。`No matching distribution found` 或缺少 wheel 时，核对 Python 版本 / 架构与离线材料；安装没有成功就先不要进入执行验收。

### 3.4 启动与确认页面

```powershell
.\start.bat
```

保持该窗口运行，打开 `http://127.0.0.1:8000`。新安装的用例、套件和计划列表可以为空，这是正常状态；首次验收不使用 `--seed-demo`，避免混入演示记录。

应看到顶部 **测试计划、测试用例、测试套件、报告中心、资源与环境、安装与配置迁移**。导航缺失时先核对地址，再按 `Ctrl+F5`，或打开 `http://127.0.0.1:8000/static/index.html?v=cross-pc#/migration`。

如端口已被占用，先核实已有服务；可在当前目录改用：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Port 8001
```

之后所有网页地址把 `8000` 改成 `8001`。不要在原服务还运行时重复启动相同端口。

默认运行数据在当前平台的 `data/`。若要显式隔离到别处，用下面命令替代 start.bat；同时指定数据目录和数据库，避免旧环境变量影响验收：

```powershell
& '.\.venv\Scripts\python.exe' backend\run.py --data-dir 'D:\验收数据\本轮' --db 'D:\验收数据\本轮\db.sqlite' --port 8001 --no-browser
```

### 3.5 按需准备引擎与项目依赖

先用核心 pytest 完成下面的校准即可。需要其他引擎时，可在可联网的目标电脑追加：

```powershell
.\install.bat -PythonExe 'C:\Python313\python.exe' -WithUI
.\install.bat -PythonExe 'C:\Python313\python.exe' -WithLocust
.\install.bat -PythonExe 'C:\Python313\python.exe' -WithVision
```

如使用已有项目自己的 Python 环境，可以直接登记它，不要求所有项目共用平台 `.venv`。业务依赖应安装到**实际被选作执行机的 Python** 中，例如：

```powershell
& 'E:\venvs\业务测试\Scripts\python.exe' -m pip install -r 'E:\业务项目\requirements.txt'
```

运行环境页面的“补充依赖模块”只是登记检查项，不会执行 pip 安装。离线使用可选引擎与业务项目时，需要提前另外准备对应依赖。

## 4. 配置本机资源：先跑通配套示例

### 4.1 准备示例项目文件

把操作包中的 **`示例项目/` 内部内容**复制到 `E:\QA\目标机 验收项目`，结果应为：

```text
E:\QA\目标机 验收项目\
└─ tests\
   └─ test_acceptance.py
```

请不要多套一层 `示例项目` 目录。此脚本有一个成功用例和一个故意失败用例，只检查执行目录和平台环境注入，不连接游戏、数据库或外部服务。

### 4.2 登记项目、Python 和执行机

打开 **资源与环境 → 管理项目与测试入口**，依次完成：

| 顺序 | 页面操作 | 本文示例填写 |
|---|---|---|
| 1 | 新增项目 → 保存项目 | 名称 `异机验收项目`；根目录 `E:\QA\目标机 验收项目`；启用 |
| 2 | 新增运行环境 → 保存入口 / 运行环境 | 名称 `异机验收 Python`；Python 为目标平台 `D:\工具\异机测试平台\platform\.venv\Scripts\python.exe`；补充依赖留空；启用 |
| 3 | 在该运行环境行点击“检查配置” | 应能找到解释器并导入 pytest |
| 4 | 在该运行环境行点击“关联执行机” | 名称 `异机验收执行机`；默认项目选 `异机验收项目`；允许引擎勾选 `pytest`；启用并保存 |

“运行环境”是登记 Python，“Executor / 执行机”是计划选择的执行配置。两者都要完成；关联执行机后再到资源与环境页面核对保存结果。

### 4.3 登记两个测试入口

仍在管理项目与测试入口页面，分别新增以下两项，所属项目均为 `异机验收项目`，类型均为 `pytest`，均启用：

| 入口名称 | 项目内相对入口 |
|---|---|
| `异机验收成功入口` | `tests/test_acceptance.py::test_should_pass` |
| `异机验收故意失败入口` | `tests/test_acceptance.py::test_should_fail` |

点击各自“检查配置”。入口填项目内相对路径，不填 `E:\...` 绝对路径，不填 Python 或 pytest 命令。所属项目下拉框为空时先保存项目并刷新页面。

### 4.4 登记被测 Environment

回到 **资源与环境 → Environment**，新增 `异机离线校准环境`，类型选择 `offline`，启用保存。离线示例不需要 HTTP 服务，host 留空、port 使用 `0`；若界面隐藏了离线无关字段，保持默认即可。

Environment 是被测服务配置，执行机是运行测试的 Python，两者含义不同。真实项目需要服务时另建对应环境，不要让真实 MMO 用例继续使用这个 offline 环境。

## 5. 导入自己的用例、套件和计划

### 5.1 先导入配套 JSON

1. 打开 **安装与配置迁移**。
2. 选择操作包里的 **`自有用例与计划示例.json`**，批次名称可填 `目标机首次校准`。
3. 点击 **导入到待关联批次**。此时尚未生成正式用例、套件和计划，也不会执行脚本。
4. 给四个资源槽选择本机资源：

| 迁移资源名称 | 目标电脑选择 |
|---|---|
| 离线校准环境 | `异机离线校准环境` |
| pytest 执行机 | `异机验收执行机` |
| 成功测试入口 | `异机验收成功入口` |
| 故意失败测试入口 | `异机验收故意失败入口` |

5. 可填名称前缀，例如 `目标机A · `。点击 **保存关联并预览**，应显示新增 **2 个用例、1 个套件、2 个计划**。
6. 刷新页面或返回迁移批次列表，再进入当前批次，确认已经保存的关联仍在；修改前缀后，应要求重新预览。
7. 重新预览通过后，点击 **确认新增这些记录**。保存回执截图；到三个列表页面核对新增内容。

套件名为“异机校准套件（含故意失败）”，其中包含两条校准用例。两个计划各引用一条，分别验收成功和失败链路；不要把整个校准套件当作必须全绿的业务回归。

同名记录会自动增加导入序号，不会覆盖已有定义。重复导入新批次会新增另一批记录；已提交批次用于查看回执，不要为“继续导入”而再次新建批次。

### 5.2 再接入目标电脑的真实项目

示例校准后，按第 4 节相同顺序登记**自己的业务项目、Python、测试入口和被测环境**。自己的脚本需要先放在目标电脑；导入 JSON 不会上传脚本。

定义来源任选一种：

- **已有平台定义**：在源平台“安装与配置迁移”选择用例 / 套件 / 计划并导出 JSON，复制到目标电脑导入，重新关联本机资源。被引用的用例会自动包含；旧引用版本已变化时，先同步源记录或取消该项选择。
- **自己编写定义**：在目标平台点击“下载 JSON 模板”或“填入示例模板”，填写自己的业务名称，关联自己登记的入口；可以先按配套 JSON 的结构编写。迁移格式为 `unified-test-platform/config`、版本为 `1`。
- **直接网页登记**：也可先在“测试用例”新建记录、加入套件、创建计划，再导出该定义并导入为新批次，用来验收自己的定义导入过程。

`resources` 是关联槽；`{"$resource":"槽ID"}` 是参数中的关联引用，计划的 `environment` / `executor` 使用槽 ID；用例 / 套件 / 计划的 `id` 只是 JSON 内部标识。**不要把源库数值 ID 或源电脑绝对路径当成目标机绑定。** `.py` 文件、任意 Excel 或其他产品的私有 JSON 不会自动转换成平台计划。

真实项目至少选择一个结果明确的业务用例。涉及账号注册、进房、数据库清理的用例，应先按项目要求准备测试服务与数据，并核对清理结果。

## 6. 执行前预检

在 **测试计划** 找到“异机校准：成功计划”，点击 **预检**；或打开计划编辑器，核对 Environment / Executor / 引用用例后点击 **预检 / 执行预览**。

核对检查时间、逐项状态和详情：

| 校准阶段检查 | 预期 |
|---|---|
| 引擎 / 参数 / 用例引用 | pytest 已注册、参数合法、引用有效 |
| 执行机与解释器 | 选的是目标机解释器、允许 pytest、依赖可用 |
| 测试入口 / 项目 | 指向刚登记的目标目录，文件与函数可用 |
| Environment | offline 环境不要求网络服务，不应为了“全绿”随便填写一个服务器 |
| 实时客户端检查 | 普通 pytest 校准不涉及 Unity / Poco，相关内容应不适用或不出现 |

预检前后核对执行记录数量，**预检本身不应新增 PlanRun / Job**。失败、未检查、资源占用都不能当作通过。

当前预检用于诊断，**不是所有失败项都会统一禁用执行按钮**。执行准备阶段还会重新检查；看到某项预检失败而执行成功时，应记录检查项、时间和运行编号并排查，不能仅凭最终绿色就把该检查勾为通过。导入预览通过也不能替代计划运行预检。

真实项目按所用服务、声明的依赖、资产和 UI 运行要求继续检查。先修复阻塞项，再发起正式验收执行。

## 7. 执行、日志和报告验收

### 7.1 成功链路

1. 执行“异机校准：成功计划”：在列表点击 **一键执行**，或编辑器点击 **保存并执行**。
2. 记录新产生的 PlanRun / Job 编号，等待结束。计划与 Job 应为 `success`，pytest 应实际执行 **1 个用例、通过 1 个**，不能只有收集结果或 0 个用例。
3. 在运行详情 / Job 点击 **日志**。应有 pytest 执行过程、选择器、运行目录的脱敏展示和 `1 passed`；脱敏路径显示 `[runtime]`、`[project]` 或省略内容时，以用例中的工作目录断言与执行机绑定共同确认本机运行。
4. 打开对应报告，核对引擎 `pytest`、计划 / Job 归属、成功状态和统计。
5. 点击产物中的 **junit.xml**，打开或下载，确认包含 `test_should_pass`，失败数为 `0`；保存报告详情和附件作为证据。

脚本打印的成功标记可能被 pytest 捕获，不要求所有 `print` 都出现在成功控制台日志里。以实际执行数量、状态、断言和 JUnit 为准。

### 7.2 故意失败链路

1. 对“异机校准：故意失败计划”先预检，再执行。
2. 预检应可以通过：检查的是运行准备条件，不会提前运行断言。
3. 执行结果应为 `failed`，pytest 实际执行 **1 个用例、失败 1 个**。
4. 日志 / JUnit 中应能找到断言与 `CROSS_PC_EXPECTED_FAILURE`，报告失败统计应一致。

这次 `failed` 是校准的预期结果，**验收检查项应记“通过”**；若平台把它显示为 `success` 才是问题。验收完成后可将这个故意失败计划归档，保留证据。

### 7.3 真实项目链路

对自己的业务计划完整重复“预检 → 执行 → 日志 → 报告 → 实际产物”。记录业务断言，例如接口返回字段、UI 到达房间、图像匹配结果或压测请求统计，不只记录“平台按钮能点击”。

报告中心按计划 / 引擎 / 状态筛选，进入报告后通过“所属执行”返回本次运行，核对编号一致。附件以当前报告实际列出的文件为准；某个项目自行写在项目目录中的 CSV 不等于已被平台归档为可下载附件。

## 8. 按需验收 Airtest、Locust、MatchEval

### 8.1 Airtest + Poco / Unity

1. 在目标电脑启动项目服务、所需 MongoDB 和 Unity 客户端。Unity Editor 进入 Play 模式、未暂停，Game 视图可用，Poco SDK 正常运行。
2. 登记 `airtest` 测试入口。已有脚本遵循 `platform_poco` 连接复用约定；项目本身的业务 fixture 如需适配，由项目维护一次完成，新增同类计划复用它。
3. 执行机允许 `airtest`，实际 Python 已安装 Airtest / Poco 与业务依赖。
4. 在 **资源与环境 → UI 设备** 配置设备、关联执行机、窗口匹配规则、Unity Editor 模式及本机 Poco 地址 / 端口。查看本机窗口，确认规则唯一匹配；使用规则动态解析窗口，不照抄源电脑句柄。
5. 配置并引用公共运行要求，声明业务模块与 MongoDB 检查，供同类用例复用。Poco 使用目标机的 loopback 地址；原项目使用 5001 时核对当前目标机监听值。
6. 导入 / 配置用例，核对 UI 套件、已登记文件、设备与执行机绑定；UI 用例使用 `airtest` 引擎。
7. 实时预检应检查窗口、GameView（Editor 场景）、Poco 层级和探测连接回收，检查不会代替业务页面复位。
8. 人工准备脚本要求的初始页面，执行并核对业务目标、日志中的 RPC 回收、截图 / 层级 / JUnit 等实际证据。再次执行前按脚本要求手动复位，并确认设备未被上一轮占用。

MMO 注册进房用例需要初始 ServerInput / PortInput / BeginBtn 页面、目标服务和测试账号清理条件。MongoDB “可连接 / 可读”不能证明拥有删除权限；是否清理成功看本次 teardown 与数据库结果。

### 8.2 Locust

登记自己的 Locust 场景、Python 与被测服务，计划选择相应环境。首次使用小规模、短时长的项目批准参数，核对请求确实到达目标服务，执行结束，日志与报告中的请求数、失败数、响应时间及实际归档 CSV 一致。脚本内自行硬编码的服务器地址仍需项目配置适配，平台 Environment 不会自动改写脚本。

### 8.3 MatchEval

登记本机模板、场景、兼容评估脚本及依赖，选择正确数据集。使用项目已知结果的图片执行，核对图像数量、算法、阈值、匹配结果及 CSV / 图片证据。图片与脚本路径可以独立配置；未知真值不能凭“运行结束”就判定算法正确。

## 9. 负向检查与重启恢复

### 9.1 缺少必要资源时给出明确错误

在没有进行中任务时，临时停用本轮专用的“异机验收执行机”，重新预检成功校准计划。应显示执行机不可用。此时若尝试执行，应被资源校验拒绝且不新增运行；保存提示与执行记录数量截图。随后恢复启用，重新预检并执行成功。只操作本轮专用资源。

这是“必要资源停用”的拒绝校验，不代表所有实时预检失败都有相同门禁；其他失败按第 6 节记录。

### 9.2 导入缺关联时保持待处理

可另建一个校验批次，不选择必需资源直接预览，页面应给出缺项，不能确认新增；用例 / 计划数量不变。补齐后重试，或放弃这个待导入批次。原先成功导入的记录保留。

### 9.3 重启恢复

1. 等待执行结束，在启动平台的 PowerShell 按 `Ctrl+C`。
2. 使用**同样的启动命令、端口、数据目录和数据库**重新启动。
3. 刷新网页，核对资源、用例、套件、计划、导入回执 / 待处理批次仍在。
4. 打开重启前成功与失败的执行记录、日志、报告和附件。
5. 对成功校准计划再执行一次，应产生新的运行编号并再次成功；旧记录与旧附件保持可读。

如果重启后全空，先核对实际数据目录 / `--db` / 环境变量，确认是否打开了另一个实例；不要重新导入掩盖问题。新导入不会带入源平台历史报告，目标机只有自己执行产生的历史是正常的。

## 10. 常见问题快速处理

| 现象 | 优先检查与处理 |
|---|---|
| 找不到 Python / `.venv` 未生成 | 确认现存 Python 完整路径、64 位、版本；重跑指定 `-PythonExe` 的安装命令并保留报错 |
| pip 网络错误 / 离线缺包 | 核对网络 / 包源，或准备匹配 Python 与 Windows 架构的 wheel；可选引擎和项目依赖另备 |
| 端口 10048 | 原服务是否还在；核实进程或改端口，勿重复启动 |
| 导航没有安装与配置迁移 | 核对当前 URL / 端口和启动目录，Ctrl+F5；使用第 3 节带查询参数的链接 |
| 所属项目 / 入口 / 资源下拉框空 | 先保存并启用项目 → Python → 执行机 → 入口，核对类型，再刷新页面 |
| 项目检查通过但缺模块 | 依赖应安装到被选作 Executor 的那个 Python，网页登记本身不会安装 |
| 导出提示用例版本已变化 | 在源平台同步套件 / 计划引用，或取消选择这条定义后重新导出 |
| 导入预览过期 / 409 | 配置、前缀或名称已变化，重新保存关联并预览，核对后提交 |
| pytest 0 个用例 / 文件找不到 | 项目根是否多套一层、选择器大小写 / 函数名、工作目录、是否只做收集 |
| 预检失败但执行成功 | 按检查项 / 时间 / Run 编号登记问题；预检并非统一门禁，不能直接判全部通过 |
| UI 套件文件不匹配 / Poco 超时 | 文件须属于目标 UI 入口；检查 Play / 暂停、窗口规则、GameView、端口、Poco 层级，不只看 TCP 开放 |
| 缺报告 / 附件打不开 | 核对 Job、准备 / 执行 / 收尾阶段错误、报告链接与数据目录；不假设每次失败都能产生完整截图 |

需要查询端口进程时，在目标电脑执行只读命令：

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen | ForEach-Object {
    Get-CimInstance Win32_Process -Filter "ProcessId=$($_.OwningProcess)"
} | Select-Object ProcessId, ExecutablePath, CommandLine
```
