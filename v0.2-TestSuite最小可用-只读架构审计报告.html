二、TestSuite 是否应该新增实体

2.1 结论：应该，但必须是"有序用例集合"，且有 3 条不变量

先回答那个尖问题：

Q：TestSuite 到底是"测试集合"，还是会逐渐变成第二个 Plan？
A：在当前代码结构下，它只能是集合 —— 因为它的所有"执行属性"都无处安放。 Plan 是 plans 表上一行，环境/执行机/资产是那一行的三个 ID 列（plans.environment_id / executor_id / asset_source_id）， 执行入口 POST /plans/{pid}/run 也只认 plan。Suite 若想变成"第二个 Plan"，就必须先获得这三列 + 自己的 run 入口 —— 那不是演化，是设计事故。

2.2 三条不变量（建议直接作为验收断言）

#不变量违反时的可观测征兆如何守住
I1 Suite 不含任何执行作用域字段（environment_id / executor_id / asset_source_id / fail_fast、超时策略、并发策略） 同一个 Suite 无法在两个不同环境下使用 suite_errors() 显式拒绝这些键（沿用 _tc_errors 拒绝 params.asset_source_id 的同一手法，router.py:299-300）
I2 Suite 不复制 Case 定义（engine / params / requires_exclusive / asset_kind 一律不出现） 改 Case 参数后 Suite 行为不变，出现"两份真相" Suite 表没有这些列；展开时从 Case 现取
I3 执行顺序权威只有一个：plans.steps[]。Suite 的顺序只在"展开的那一瞬间"起作用 同一份工作出现两种不同执行次序 本批不引入 suite_ref 步骤形态（见 §7）；Suite 展开后即被替换成普通步骤

2.3 建议的关系图（fut = 本批新增）

TestCase
定义层（已有）→ TestSuite
有序 case_ref 集合（新）→ 展开 edit-time→ Plan steps[] 仍是唯一顺序源→ PlanRun→ Job→ Report
与用户给出的目标关系图完全一致，唯一补充是：Suite 与 Plan 之间那一跳发生在"编辑期"，不是"执行期"。 这让 Suite 在运行时彻底不存在 —— 三个 Runner、调度器、报告中心都不需要知道它。

三、test_suites 表结构

CREATE TABLE IF NOT EXISTS test_suites (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    description TEXT DEFAULT '',
    cases       TEXT NOT NULL DEFAULT '[]',   -- 有序：[{id, revision, fingerprint}, ...]
    fingerprint TEXT NOT NULL DEFAULT '',     -- 定义指纹（见 §6）
    revision    INTEGER NOT NULL DEFAULT 1,
    enabled     INTEGER NOT NULL DEFAULT 1,
    owner       TEXT DEFAULT 'local',
    tags        TEXT DEFAULT '[]',
    created_at  TEXT,
    updated_at  TEXT
);
CREATE INDEX IF NOT EXISTS idx_ts_enabled ON test_suites(enabled);

3.1 字段逐条裁决

字段类型必填裁决理由（对照实际代码）
idINTEGER PK AUTOINCREMENT是保留与全部实体一致
nameTEXT是保留与 test_cases.name 对称；参与定义指纹；应用层查重（router.py:306-308 同款）
descriptionTEXT否保留不参与指纹 —— 与 TestCase 完全一致
casesTEXT（JSON）是新增本表的核心。有序数组，元素是 {id, revision, fingerprint}
fingerprintTEXT是新增没有它就无法判定"定义是否变化"，revision 规则就退化成逐字段手写比较 —— 那正是 v0.2 已经否掉的写法
revisionINTEGER是保留沿用 TestCase/Plan 的版本语义
enabledINTEGER是保留与 test_cases.enabled 同义（停用的 Suite 不允许展开）；不入指纹、不 bump revision
ownerTEXT否保留与 TestCase 对齐，不入指纹
tagsTEXT（JSON）否保留与 TestCase 对齐，不入指纹
created_at / updated_atTEXT是保留沿用 _now()
明确不加：environment_id / executor_id / asset_source_id / fail_fast / engine / params / notes / status —— 前三项属 Plan（I1）；engine 可由 cases 派生且 Suite 允许跨引擎；params 属 Case（I2）；notes 与 description 重复（v0.2 对 TestCase 已用同一理由否决）；status 是 Job 的概念
与用户建议字段的差异只有一处：必须补 fingerprint。 用户列的 9 个字段（id/name/description/revision/enabled/owner/tags/created_at/updated_at）都对，但没有 fingerprint 就无法实现用户自己要求的 "Suite definition fingerprint 至少包含 name + ordered case_ref list"。test_cases 同样有这一列（db.py:160）—— 对称。

四、test_suite_cases 表结构 —— 裁决：不建

4.1 四条来自本项目自身的硬证据

#证据来源含义
1 全库零 FOREIGN KEY PRAGMA foreign_key_list(*) 全空；db.py 无任何 FOREIGN KEY 声明 关联表拿不到任何引用完整性收益（无约束、无级联、无阻止删除），只剩 join 成本
2 同样的需求已经用 JSON 列解决过一次 plans.steps：有序的、元素带 engine/name/params 的集合，没有 plan_steps 表 v0.2 审计已经否决过 plan_cases；Suite 是同一形状的问题，用同一答案

六、Suite fingerprint 规则

6.1 规则（复用 _h()，不另造哈希）

def suite_fingerprint(name: str, cases: list) -> str:
    """Suite 定义指纹。复用项目统一的 _h()（sha256 截断 12 位）。"""
    norm = [{"id": int(c["id"]),
             "revision": int(c.get("revision") or 1),
             "fingerprint": str(c.get("fingerprint") or "")} for c in (cases or [])]
    return _h("suite", name or "",
              json.dumps(norm, sort_keys=True, ensure_ascii=False))
内容是否进入指纹理由
name进与 test_case_fingerprint 一致（config_center.py:439 把 name 计入）
cases 有序数组的 {id, revision, fingerprint}进定义的全部实质内容；顺序参与，故用 list 顺序而非 sort_keys 排序数组本身（仅对元素内键排序）
id / revision(Suite 自身) / created_at / updated_at不进与 TestCase 完全一致：版本号与时间戳不是"内容"
description / tags / enabled / owner不进与 TestCase 完全一致

6.2 三个指纹的职责边界（必须在 UI 与文档中显式区分）

指纹存在哪回答什么问题何时算本批
定义指纹（Case） test_cases.fingerprint 这个测试定义是什么 保存用例时 已有（v0.2 一阶段）
定义指纹（Suite） test_suites.fingerprint 这个测试集合（有序）是什么 保存套件时 本批新增
内容指纹 jobs.config_snapshot.content 本次执行实际面对的受控脚本/素材内容是什么 PlanRun 创建阶段，算一次 已有（v0.2 一阶段）
计划快照指纹 plan_runs.plan_snapshot.snapshot_fingerprint 本次执行时的计划定义是什么 PlanRun 创建时 已有
Suite 指纹绝不代替内容指纹。 Suite 指纹是"定义层"的（我引用了哪些 Case 的哪些版本）； 内容指纹是"执行层"的（那些 Case 指向的脚本/素材字节是什么样的）。 前者不读盘、成本可忽略；后者要读文件、成本高几个数量级 —— 混用会立刻污染性能模型（这一点在 v0.2 一阶段已经分解过一次，本批不再合并）。

七、Suite → Plan 的展开方式

7.1 三条候选路线

路线做法评价
A（推荐）编辑期展开 Plan Editor 里点「添加套件」→ 选 Suite → 前端调用只读 POST /api/suites/{sid}/expand 拿到 N 个 case 步骤 → 就地插入编辑器，用户可继续增删改 → 保存时写入 plans.steps[]（就是今天的 case_ref 形态） 不回传、不新增步骤形态、不新增透传点、Runner/调度器/报告中心零改动；顺序权威唯一（I3 成立）
B 保存期展开
plans.steps 里存 suite_ref，保存时后端展开		 Plan 里出现第三种步骤形态 {suite_ref:{...}} 编辑器看不到展开后的样子（用户无法逐条微调）；plan_snapshot 里的步骤数与 plans.steps[] 长度不一致 → "存储形态 = 快照来源"这条模型被打破；需给 PlanStep 加新形态 + 新透传点
C 执行期展开 run 时才展开 suite_ref 更差：预检/编辑器与实际执行不一致，违反 v0.1 已确立的"预检结果 = 真实执行结果"
采用 A。这也正是用户 §5 里偏向的那条："如果 Suite 可以在进入 Plan 时展开成多个 TestCase Step，那么优先采用 Suite → 展开 Case → Plan Steps → 现有 TestCase expansion → Plan Snapshot"。 本审计确认该路线在当前代码下不仅可行，而且是唯一不破坏既有不变量的路线。

改 被测脚本/素材（如 locustfile.py）不变由 config_snapshot.content 记录当时内容指纹（v0.2 一阶段修复的 P0）
改 Executor / Environment不变jobs.config_snapshot 已固化脱敏配置（v0.1 机制）
结论：加了 Suite，历史不可变性零削弱。 因为 Suite 只影响"plans.steps[] 是怎么被写出来的"，不影响"写出来之后怎么被固化"。 §8.1 里 PlanRun 以下的部分与今天逐字节同构。

8.3 一个必须承认的取舍

编辑期展开意味着：Case 改了之后，已经展开过的 Plan 不会自动跟随（Plan 里 pin 的是旧 revision，执行时会被 _expand_case_steps 拦下并报错，要求重新保存计划）。

评价
优点与 case_ref 今天的语义完全一致（今天直接引用 Case 也是这个行为）→ 不引入新心智模型
优点历史绝对可复现（§8.2 第一行）
代价Case 改动后需"重新展开并保存计划"。可通过 UI 显示「本计划引用了 N 处已过期的用例引用」来缓解（P1，见 §15）
被否决的替代让 Plan 在执行期跟随 Case 最新版 → 直接推翻 case_ref 的 pin 语义，历史漂移。不可接受

九、Plan Editor 如何集成

9.1 集成方式：只加一个按钮，不加新步骤形态

项现状（index.html:676-683）本批改动
按钮区 添加内联步骤 + 添加用例步骤 + 添加套件（下拉选择已启用 Suite）
步骤形态 kind:'inline' / kind:'case'（index.html:622-625） 不变 —— 套件展开后产生的就是 kind:'case' 步骤
payload plPayload() 输出两种形态（index.html:871-885） 不变 —— 透传点 9 零改动
载入映射 按 s.case_ref 是否存在分流（index.html:645-649） 不变 —— 透传点 8 零改动
校验 plSave() 检查"步骤未选择 TestCase"（index.html:911-912） 无需改（展开后的步骤都带 case_ref）
这是本设计最省的地方：Plan Editor 只需增加一个"批量插入"的入口动作，其余全部复用。 展开后的步骤与用户手点「添加用例步骤」产生的步骤没有任何区别，所以用户可以对展开结果自由地删除某一条、调整顺序、改覆盖参数。

9.2 交互细节建议

  • 选完 Suite 后，在插入点当前位置插入 N 个步骤（不是追加到末尾），符合"我在这里想要这一组"的直觉。
  • 插入后给一个提示条：已从套件「X」rev3 展开 4 个用例步骤（可以单独调整）。
  • 若展开失败（Case 已停用/版本漂移），不插入任何步骤，弹出后端返回的原始错误（与预检同一套措辞）。
  • 不做拖拽、不做套件内联展示、不做"实时同步套件变更"。

9.3 一个必须说清的限制

若 Suite 内的用例跨引擎（例如同时含 pytest 与 locust），展开后的 Plan 就会变成一个多引擎计划。这在当前平台是被支持的（真实库里已存在三引擎计划 id=12），但有前置条件：

  • Plan 的 Executor 必须在其 allowed_runners 中允许全部涉及的引擎 —— 否则预检会如实报 执行机不允许 {engine}（config_center.py:1159）；
  • Plan 的 AssetSource 只会对 kind 匹配的引擎生效（router.py:747-752 的 _asset_key_for 按 kind 返回，不匹配则返回空串）—— 这是既有行为，不是缺陷。

→ 建议在 UI 的套件选择器里显示每个 Suite 涉及的引擎集合，避免用户选完才发现预检不过。

① P1-1 的 suite_ref 溯源键做不做？
